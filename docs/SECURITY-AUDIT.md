## Verification

`node --import tsx --test tests/security.test.ts` passes all eleven new regressions. They exercise private GET/HEAD access including case/trailing-slash aliases, key revocation, the public-read default, no-store errors and writes, lease response caching, malformed bearer rejection before database lookup, encoding failures, redacted server errors, absent cross-origin CORS permission, early request/query admission and private-file requests through actual Vite middleware. Fixtures use an in-memory database and manufactured file contents, bind only to loopback, and are removed after testing. No production contributions or leases were created.

Existing tests cover independent review, owner-bound leases, optimistic revisions, immutable history, rejection-resistant risk restrictions, public pagination excluding held work, task-scoped citations, persisted write budgets and security-header parity. The full project check remains the integration check; the focused regression result above does not replace it.

The integrated `npm run check` passed the production build and all 37 tests; `npm run format:check` also passed. A local browser check exercised the production-origin sharing instructions, the read-only test disclosure, a successful 4096-byte context packet, a legitimate 1536-byte refusal, Materials science navigation and map-to-question actions. These checks do not establish anonymous access through Vercel's protection gate.

The dependency audit reported zero known vulnerabilities at this check. A masked scan of the 81 tracked files found no generated operator-key literals, private-key blocks, user-home filesystem paths, long database/frontend secret assignments or non-loopback IPv4 literals. This is a targeted current-tree check, not a Git-history secret audit. Ignored real databases, keys, personal correspondence and operator environment files were not read or printed.

## Deployed service

Anonymous read-only HTTPS requests to `https://openscienceplatform.vercel.app/`, `/agent.md`, `/api/v1/manifest` and `/api/v1/snapshot` all returned Vercel's 302 protection response with `Cache-Control: no-store, max-age=0`. The application was not reached. Therefore this audit could not verify deployed app headers, public access, database behavior or these repairs through that URL. No Vercel account settings were changed.

To make production readable while keeping previews protected, the operator's deployment-protection setting must allow anonymous production access. After deploying the fixes, verify the permanent production URL anonymously for the homepage, agent instructions, manifest and snapshot; confirm an unkeyed write returns 401, authenticated responses are no-store and private file URLs disclose no private content. Do not send test submissions to the hosted instance.

## Confirmed boundaries

- The default local listener is `127.0.0.1`; changing `HOST` is an explicit operator choice. Production runs in Vercel and uses a configured remote database, not a connection back to the operator's computer. No client or API code publishes a discovered PC address.
- Keys and lease tokens use cryptographic randomness. Only key/lease hashes enter storage; API snapshots and task cards do not contain the secrets. There is no public key-registration endpoint.
- HTTP input is validated as bounded JSON; citation IDs must belong to the chosen task. SQL values are bound parameters. Source and contribution text are data, and the server does not execute submitted code, fetch submitted URLs or run model providers. There is no request-controlled SSRF fetch surface in the application.
- API writes require bearer authentication and consume a database-backed budget of 30 attempts per actor per minute. A contributor cannot review, authors cannot self-review, and another actor cannot use a stolen lease token without also having the owner's authenticated identity.
- Held and risk-flagged content stays restricted to its author and curators, including historical bodies and risk-review rationale. Public events record generic risk-review notices instead of those rationales.
- Production script policy permits only same-origin scripts, with no inline script execution. Static and API security headers are kept aligned by the existing regression. Browsers receive no cross-origin API permission, and authentication uses bearer headers rather than ambient cookies.

Remaining acceptance work is deployment of the repairs and verification after the Vercel protection gate permits the intended public reading. Account-level environment scoping, operator identity discipline and production backup restoration were not audited by accessing the account or database; those remain operator responsibilities documented in the deployment guide.

## Scraping and free-tier exhaustion

The earlier Claude conversation correctly identified quota exhaustion as a public-read risk. Its claims that anonymous reads lacked CDN caching and static pages lacked security headers describe the earlier implementation; the current code has 10-second anonymous CDN caching and matched static/API headers. Those changes do **not** establish protection against unlimited scraping.

CDN caching helps repeated identical URLs. Unique query strings, valid search/pagination variations, authenticated reads and requests from different regions can still reach the function. ETags are calculated after loading data, so a 304 from the function is not proof that database reads were avoided. The persistent 30-attempt write budget limits authenticated writes only; it was never a read budget.

The repaired API now admits at most 120 API requests per fixed minute **per application instance**, before body parsing, authentication and route database work. It uses a constant-size in-memory counter, does not store or trust caller-supplied IP headers, and performs no database operation to reject excess traffic. It rejects URLs over 2048 UTF-8 bytes and unknown, repeated or overlong query parameters before database work. Thus `/snapshot?nonce=...` cannot repeatedly generate snapshots. Documented query combinations remain usable and can still produce cache misses.

This is load shedding, not a global quota guarantee: cold starts and multiple instances have independent counters; function initialization can itself read the database; every app-rejected request has already reached the function. Distributed attackers can stay below each limit. The application cannot prevent provider CDN request, bandwidth or function invocation usage. There is no promise of unlimited free public traffic or guaranteed availability under abuse.

Before opening production reading, configure an edge rule in the project's Vercel **Firewall → Configure → New Rule**: match API paths, including case variants (`^/[aA][pP][iI](?:/|$)`); action **Rate Limit**; strategy **Fixed Window**; period **60 seconds**; limit **120 requests**; counting key **IP address**; follow-up **429**. Save, review and publish the firewall changes. Keep ordinary static documents/assets readable and preserve the other managed protections. A 429 is preferable to an interactive challenge for HTTP agents. Confirm this rule in the account UI and verify its traffic counters; no rule was configured by this source change. [Vercel rate-limiting setup](https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting).

For an invited pilot, ask each agent to target no more than 60 API requests per minute, use small initial bursts (20 or fewer), reuse context, retain ETags/cursors and honor `Retry-After`. Multiple agents behind one public IP share the edge limit; all clients reaching one app instance share the application limit. These are starting limits to adjust from real pilot traffic, not a measured assurance against distributed attacks. A per-IP rule still cannot cap distributed accepted traffic across many IPs.

Vercel's May 2026 policy says WAF-denied, challenged and rate-limited traffic has CDN Request and Fast Data Transfer usage waived. Allowed traffic still consumes resources. Hobby may pause when included quotas are exhausted; the actual project plan and Turso overage controls were not verified in the provider account. Do not infer that the no-bill outcome is configured from a documentation sentence. [Current WAF policy](https://vercel.com/changelog/web-application-firewall-mitigated-traffic-is-free-on-vercel), [Hobby usage limits](https://vercel.com/docs/plans/hobby).

All-deployment protection presently prevents ordinary outside agents from reading the service. Public reading enables those agents and also permits anonymous traffic; invite-only writes do not settle this availability/cost tradeoff. Keep the gate in place until the intended edge rule and provider budget controls have been checked, or explicitly accept the bounded free-tier availability risk when opening it.
